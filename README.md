# ReturnGuard Agent

Razorpay AI Buildathon 2026 - Track 2 (AI Risk Manager).

Scores every order at checkout for return probability, then decides and
executes a bounded action (allow / restrict COD / flag for review) within
a per-hour cap - not just a score someone still has to act on. Every
decision, and every human override, is written to a permanent audit log.

**Live demo:** https://returnguard-agent-j5svwedftceap23mh5tb6d.streamlit.app
(backend: https://returnguard-backend-1nop.onrender.com - free-tier, may
take ~30-60s to wake up after idling; see "Deploying live" below)

## Two datasets, one pipeline

ReturnGuard runs on either of two datasets, selected by a `--dataset
{synthetic,real}` switch that threads through the whole pipeline (data
prep, training, evaluation, error analysis, and the served model):

- **synthetic** (default) - generated by `scripts/generate_data.py` with
  a deliberately noisy latent-risk function. This is what every number in
  the "Results" section below refers to.
- **real** - the [Olist Brazilian E-Commerce
  dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce),
  adapted by `scripts/prepare_real_data.py`. See "Real (Olist) data path"
  below.

The two paths are fully independent and independently reproducible from a
clean checkout. They never share data files or model files:

    data/synthetic/{train,val,test}.csv     models/xgboost_model_synthetic.joblib
    data/real/{train,val,test}.csv          models/xgboost_model_real.joblib
    data/olist_raw/*.csv   (the 7 raw Kaggle Olist CSVs)

### Real numbers are NOT comparable to synthetic numbers

Do not read the real-data metrics as "the model got worse". The two
datasets are different problems:

- **Different base rate.** Synthetic returns run ~35%; the Olist proxy
  label (`review_score <= 2`) runs ~12-15%, and drifts down across the
  temporal split. A precision floor tuned for a 35% positive rate is
  meaningless at 12%, which is exactly why `scripts/train.py` uses
  *different, per-dataset* guardrail values (synthetic:
  `min_precision=0.40, max_flag_rate=0.40`; real: `min_precision=0.20,
  max_flag_rate=0.35`).
- **Different label.** Synthetic `was_returned` is a real (if noisy)
  return event. Olist has no return flag at all - `was_returned` there is
  a *proxy* for "customer was unhappy enough to leave a 1-2 star review".
  Some of those are returns; some aren't; some real returns left no bad
  review. The label itself is noisier.
- **Different feature availability.** `discount_pct` does not exist in
  Olist - it is carried in the schema as an all-NaN dead column (imputed
  away) so the pipeline stays uniform. `review_score_avg` is redefined
  from a customer-level to a product-level average (only ~3% of Olist
  customers are repeat buyers). `customer_prior_return_rate` is missing
  for ~97% of real rows for the same reason. `payment_method` has no true
  UPI/COD - `boleto` (a pre-shipment bank slip) is mapped to `"COD"` as
  the closest real analog, and that mapping is a judgement call.
- **Different geography and currency.** Olist is Brazil, 2016-2018, in
  BRL; the synthetic set is a notional INR store. The cost constants
  (50 / 250 per FP / FN) are not re-derived for Olist, so the "net value"
  figure in the real report is illustrative only.

Held-out test metrics live in **separate** report files that never
overwrite each other: `evaluation/eval_report_synthetic.md` and
`evaluation/eval_report_real.md`.

## Results (held-out test set, never used during training or tuning)

These are the **synthetic** numbers (the default dataset).

- Precision: 0.479
- Recall: 0.619 (catches 61.9% of actual returns)
- F1: 0.540
- ROC-AUC: 0.671
- Net value: ~32,650 INR on a 773-order batch (value of returns caught
  minus false-positive friction cost)
- 45.2% of orders receive some action (42.6% flagged for review, 2.6%
  COD-restricted); 54.9% pass straight through

Full report: evaluation/eval_report_synthetic.md (and eval_report_real.md
for the Olist path)
Full 13-day plan and design rationale: docs/buildathon_plan.md

## A note on this being a revised model (read this - it matters)

The model below is a REVISED version, updated on Day 12 after the
original Day 10 evaluation (original numbers: precision 0.427, recall
0.815, 66.6% of orders flagged). The original threshold technically
followed the evaluation methodology but produced an operationally
unworkable review queue - two-thirds of all orders were flagged, and
the customer-facing restrict_cod action almost never fired (0 orders on
the original held-out test set).

We made three changes, all developed using train.csv and val.csv only:

  1. Added has_return_history: a new feature capturing whether we have
     ANY prior-return data for a customer, separate from the (possibly
     imputed) rate itself.
  2. Ran a small, bounded hyperparameter search (5 candidates) on
     train/val only.
  3. Added a flag-rate cap (max 40%) to threshold selection, so the
     policy can no longer flag an unworkable fraction of all orders
     regardless of what the raw cost formula alone would prefer.

test.csv was then evaluated exactly ONE more time, to get an honest
number for the model we actually ship - not repeatedly, and not to pick
between variants. This is a deliberate, documented, single exception to
the "look once" rule, made so the reported numbers reflect the model
we're actually submitting rather than a stale number for a version we
no longer use.

Tradeoff versus the original: recall dropped (81.5% -> 61.9%) but
precision improved (42.7% -> 47.9%), the review queue nearly halved
(66.6% -> 45.2% of orders), and restrict_cod went from functionally
disabled to firing on 2.6% of orders. This is a deliberate choice
favoring an operationally workable system over maximizing raw recall.

## What broke, and what we learned

Error analysis (evaluation/error_analysis.py) on the held-out test set
found a clear, explainable pattern: the model leans heavily on two
signals - discount percentage and whether the category is size-related
(apparel/footwear). This causes it to over-flag discounted apparel
orders that turn out fine (false positives), while under-catching
returns driven by other factors in non-apparel, low-discount orders
(false negatives). See evaluation/error_analysis.py output for concrete
examples with SHAP explanations.

Separately: the FIRST attempt at threshold tuning (Day 6) maximized a
raw cost formula with no operational constraint, and it flagged 91% of
orders - mathematically "optimal" under that formula, but useless as a
real review queue. Adding a precision floor got that down to 66%, which
was still too high; adding an explicit flag-rate cap (Day 12) was what
actually fixed it. Worth remembering: a metric-optimal answer isn't
automatically an operationally sane one.

## Known limitations

- 47.9% precision means roughly half of flagged orders are false alarms
  - a deliberate tradeoff favoring recall over precision, since a missed
  return (250 INR estimated cost) is more expensive than unnecessary
  review friction (50 INR estimated cost) - but this is now balanced
  against a flag-rate cap so the tradeoff stays operationally workable.
- restrict_cod (the customer-facing action) still fires conservatively
  by design (2.6% of orders) - it requires 65%+ precision among COD
  orders specifically.
- The headline numbers above are on fully synthetic data (generated by
  scripts/generate_data.py with a deliberately noisy latent-risk
  function). A second, fully working real-data path exists
  (`--dataset real`, the Olist dataset) - see "Two datasets, one
  pipeline" above for why its numbers are a different problem, not a
  regression.
- The dashboard's "Recent Agent Decisions" and every queue read live from
  the backend API (`/decisions`, `/review-queue`, `/audit-log`), not
  browser session state - the permanent record is the `audit_log` table.
  "Append-only" means the app only ever INSERTs into it (an override is a
  new row linked to the action it supersedes); it is a SQLite table, not
  cryptographically immutable.
- The model was revised once after the initial evaluation (see above) -
  test.csv was consulted a second time as a result, which is a
  documented, deliberate exception to the single-look protocol used
  everywhere else in this project.

## Setup

    python -m venv venv
    source venv/bin/activate          (Windows: venv\Scripts\activate)
    pip install -r requirements.txt

## Run it end to end - synthetic (default)

    python -m scripts.generate_data                      # regenerate synthetic data -> data/synthetic/ (optional, already included)
    python -m scripts.train --dataset synthetic          # -> models/xgboost_model_synthetic.joblib
    python -m evaluation.evaluate --dataset synthetic    # -> evaluation/eval_report_synthetic.md
    python -m evaluation.error_analysis --dataset synthetic

### Run the frontend (Streamlit dashboard)

The frontend talks only to the backend API, so start the backend first.
Use **two terminals**, both from the repo root with the venv active:

Terminal 1 - the API (must be up before the dashboard can score anything):

    # macOS / Linux
    RETURNGUARD_DATASET=synthetic uvicorn backend.main:app --reload

    # Windows PowerShell
    $env:RETURNGUARD_DATASET="synthetic"; uvicorn backend.main:app --reload

Terminal 2 - the dashboard:

    streamlit run frontend/app.py

Then open the dashboard at http://localhost:8501 (Streamlit also prints
the URL). The sidebar shows the agent status, a green "connected ·
synthetic" pill once it reaches the API, and the current hourly action
usage; if terminal 1 isn't running yet you get a compact "Backend
unavailable" bar with a Retry button instead of a wall-of-text error.

The dashboard is an **agent operations console**, not a scoring
calculator. It has six views (sidebar): **Dashboard** (run a decision +
see the full pipeline: return probability → risk level → agent decision →
hourly-cap check → action execution → audit log), **Decision Queue** (all
automated decisions, with a per-order pipeline timeline), **Review Queue**
(orders the agent flagged for a human, with approve / override actions),
**Audit Log** (the append-only `audit_log` table with filters),
**Metrics** (agent-operational counts, kept separate from model
performance), and **Settings** (read-only policy + cap config). Dark
theme lives in `.streamlit/config.toml`.

- `--dataset` and `RETURNGUARD_DATASET` both default to `synthetic`, so
  the bare `uvicorn backend.main:app --reload` also works.
- If the API runs on a non-default host/port, point the frontend at it
  with `RETURNGUARD_API_URL` (default `http://127.0.0.1:8000`).

API docs (Swagger UI): http://127.0.0.1:8000/docs

## Real (Olist) data path

One-time: download the [Olist Brazilian E-Commerce
dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) and
put these 7 CSVs in `data/olist_raw/` (already included in this repo):

    olist_orders_dataset.csv          olist_order_payments_dataset.csv
    olist_order_reviews_dataset.csv   olist_customers_dataset.csv
    olist_order_items_dataset.csv     olist_products_dataset.csv
    product_category_name_translation.csv

Then the same four steps, with `--dataset real`:

    python -m scripts.prepare_real_data --raw-dir data/olist_raw --out-dir data/real
    python -m scripts.train --dataset real               # -> models/xgboost_model_real.joblib
    python -m evaluation.evaluate --dataset real          # -> evaluation/eval_report_real.md
    python -m evaluation.error_analysis --dataset real

Serve the real-data model:

    RETURNGUARD_DATASET=real uvicorn backend.main:app --reload

`GET /health` reports which dataset the backend is serving
(`{"status": "ok", "dataset": "real", ...}`), and the Streamlit sidebar
shows it. `python -m scripts.train --dataset synthetic` and
`--dataset real` can be run in either order, any number of times -
neither touches the other's data, model, or report files. What the Olist
adapter maps and why is documented at the top of
`scripts/prepare_real_data.py`; **its metrics are not comparable to the
synthetic ones** (see "Real numbers are NOT comparable" above).

## Deploying live

Two services, deployed independently:

**Backend (FastAPI) -> Render.** The repo includes a `Dockerfile` and
`render.yaml` blueprint. In the Render dashboard: New -> Blueprint,
point it at this repo, and it picks up `render.yaml` (free plan, serves
the synthetic model, health check on `/health`). Note the free plan has
no persistent disk, so `returnguard.db` resets on redeploy/idle
spin-down - fine for a demo; upgrade to a paid plan and add a disk (see
comments in `render.yaml`) for a durable audit log. Once deployed, note
the service URL (e.g. `https://returnguard-backend.onrender.com`).

**Frontend (Streamlit) -> Streamlit Community Cloud.** New app -> point
it at this repo, main file path `frontend/app.py`. In the app's Secrets
settings, add (see `.streamlit/secrets.toml.example`):

    RETURNGUARD_API_URL = "https://returnguard-backend.onrender.com"

**Lock down CORS (recommended once you have the Streamlit URL):** set
`RETURNGUARD_ALLOWED_ORIGINS` on the Render service to your Streamlit
app's exact origin (comma-separate for more than one) instead of the
default `*`, then redeploy the backend.

## Tests

    pytest -v

The suite covers BOTH dataset paths. Synthetic tests run whenever
`models/xgboost_model_synthetic.joblib` exists; the parametrized
real-schema cases (backend scoring a discount_pct-less order, real
end-to-end pipeline, real SHAP reasons) run when
`models/xgboost_model_real.joblib` exists and skip otherwise. With both
models trained: 25 passing, 2 skipped.
