# ReturnGuard Agent

Razorpay AI Buildathon 2026 - Track 2 (AI Risk Manager)

Scores every order at checkout for return probability, then decides and
executes a bounded action (allow / restrict COD / flag for review) within
a per-hour cap - not just a score someone still has to act on. Every
decision, and every human override, is written to a permanent audit log.

## Results (held-out test set, never used during training or tuning)

- Precision: 0.479
- Recall: 0.619 (catches 61.9% of actual returns)
- F1: 0.540
- ROC-AUC: 0.671
- Net value: ~32,650 INR on a 773-order batch (value of returns caught
  minus false-positive friction cost)
- 45.2% of orders receive some action (42.6% flagged for review, 2.6%
  COD-restricted); 54.9% pass straight through

Full report: evaluation/eval_report.md
Full 13-day plan and design rationale: razorpay_buildathon_plan.md

## A note on this being a revised model (read this - it matters)

The model below is a REVISED version, updated on Day 12 after the
original Day 10 evaluation (original numbers: precision 0.427, recall
0.815, 66.6% of orders flagged). The original threshold technically
followed the evaluation methodology but produced an operationally
unworkable review queue - two-thirds of all orders were flagged, and
the customer-facing restrict_cod action almost never fired (0 orders on
the original held-out test set).

We made three changes, all developed using train.csv and val.csv only:

  1. Added has_return_history: a new feature capturing whether we have
     ANY prior-return data for a customer, separate from the (possibly
     imputed) rate itself.
  2. Ran a small, bounded hyperparameter search (5 candidates) on
     train/val only.
  3. Added a flag-rate cap (max 40%) to threshold selection, so the
     policy can no longer flag an unworkable fraction of all orders
     regardless of what the raw cost formula alone would prefer.

test.csv was then evaluated exactly ONE more time, to get an honest
number for the model we actually ship - not repeatedly, and not to pick
between variants. This is a deliberate, documented, single exception to
the "look once" rule, made so the reported numbers reflect the model
we're actually submitting rather than a stale number for a version we
no longer use.

Tradeoff versus the original: recall dropped (81.5% -> 61.9%) but
precision improved (42.7% -> 47.9%), the review queue nearly halved
(66.6% -> 45.2% of orders), and restrict_cod went from functionally
disabled to firing on 2.6% of orders. This is a deliberate choice
favoring an operationally workable system over maximizing raw recall.

## What broke, and what we learned

Error analysis (evaluation/error_analysis.py) on the held-out test set
found a clear, explainable pattern: the model leans heavily on two
signals - discount percentage and whether the category is size-related
(apparel/footwear). This causes it to over-flag discounted apparel
orders that turn out fine (false positives), while under-catching
returns driven by other factors in non-apparel, low-discount orders
(false negatives). See evaluation/error_analysis.py output for concrete
examples with SHAP explanations.

Separately: the FIRST attempt at threshold tuning (Day 6) maximized a
raw cost formula with no operational constraint, and it flagged 91% of
orders - mathematically "optimal" under that formula, but useless as a
real review queue. Adding a precision floor got that down to 66%, which
was still too high; adding an explicit flag-rate cap (Day 12) was what
actually fixed it. Worth remembering: a metric-optimal answer isn't
automatically an operationally sane one.

## Known limitations

- 47.9% precision means roughly half of flagged orders are false alarms
  - a deliberate tradeoff favoring recall over precision, since a missed
  return (250 INR estimated cost) is more expensive than unnecessary
  review friction (50 INR estimated cost) - but this is now balanced
  against a flag-rate cap so the tradeoff stays operationally workable.
- restrict_cod (the customer-facing action) still fires conservatively
  by design (2.6% of orders) - it requires 65%+ precision among COD
  orders specifically.
- Training data is fully synthetic (generated by scripts/generate_data.py
  with a deliberately noisy latent-risk function) - real-world return
  patterns would need real data to validate against.
- The "recent scored orders" queue in the dashboard lives in the browser
  session only; the permanent record is the audit_log table.
- The model was revised once after the initial evaluation (see above) -
  test.csv was consulted a second time as a result, which is a
  documented, deliberate exception to the single-look protocol used
  everywhere else in this project.

## Setup

    python -m venv venv
    source venv/bin/activate          (Windows: venv\Scripts\activate)
    pip install -r requirements.txt

## Run it end to end

    python -m scripts.generate_data          # regenerate synthetic data (optional, already included)
    python -m scripts.train                    # train + calibrate + tune thresholds
    python -m evaluation.evaluate               # held-out test evaluation
    python -m evaluation.error_analysis         # look at what the model gets wrong

Then, two terminals:

    uvicorn backend.main:app --reload          # terminal 1: the API
    streamlit run frontend/app.py              # terminal 2: the dashboard

Dashboard: http://localhost:8501
API docs:  http://127.0.0.1:8000/docs
